# CETFind Interactive Code Explorer (local-only MVP)

## Goal

Show the actual execution path behind a user action, with source-linked steps that can be inspected one by one. This is not just a file dependency graph.

## Current verified search path

Based on `docs/ARCHITECTURE_CURRENT.md` and the current implementation:

1. The browser collects course, percentile, optional city, sort, page and page size in `site/index.html`.
2. The browser sends a request to `GET /api/search`.
3. `backend/api.py::search_colleges` applies `check_rate_limit(request)`.
4. It builds a cache key and calls `_PUBLIC_CACHE.get_or_set(...)`.
5. On a cache miss, `_search_colleges_uncached` obtains the active database engine and validates the course against `available_public_courses(engine)`.
6. `src/cet_cap/queries.py::search_college_summary_page` runs the bounded, parameterized PostgreSQL summary query.
7. The backend returns early if the page is empty; otherwise it loads page-scoped metadata and builds `CollegeCard` results, including safe/borderline/reach status.
8. FastAPI validates/serializes `SearchResponse`; the browser renders the response.

This is a **source-derived path**, not a runtime trace. Cache hits skip the uncached database path; invalid inputs and exceptions produce different paths. The explorer must never label a possible path as an observed execution.

## MVP acceptance criteria

- Load a trace JSON file generated by a local run.
- Display ordered execution events and a navigable call/step graph.
- Clicking an event shows its original source file, line number, source excerpt, event kind, caller/callee, and captured locals.
- Distinguish observed events from static/inferred relationships.
- Support step-forward/back and search/filter by file/function/event.
- Redact secret-like variable names by default; do not trace production requests.
- Keep the explorer local-only and opt-in. Do not add public routes, modify the deployed app, or send source/trace data to a third party.
- Trace storage must be bounded; large loops need event limits and a clear truncation marker.

## Important implementation boundary

A useful complete version needs two data sources:

- **Static source index:** call sites, function definitions, branches, imports, and file/line links.
- **Opt-in runtime trace:** actual line/call/return/exception events and safe snapshots for a specific local test request.

Python tracing can impose substantial overhead and can expose personal data in local variables. First support controlled local test runs; do not enable it in production. Database tracing should record query shape and duration, not credentials or sensitive parameter values by default.

## Repository areas to trace first

- Frontend: `cet/site/index.html` — search event and `fetch(.../api/search)`.
- Route and cache: `cet/backend/api.py` — `search_colleges`.
- Search implementation: `cet/backend/api.py` — `_search_colleges_uncached`.
- Query implementation: `cet/src/cet_cap/queries.py` — `search_college_summary_page`.
- Tests: `cet/tests/test_api_units.py`, `cet/tests/test_public_cache.py`, and database-backed integration tests.

## How to validate

1. Generate a trace only against a local test database with synthetic data.
2. Compare the trace to the source and tests.
3. Test cache hit, cache miss, invalid course, empty results, database unavailable, and exception paths separately.
4. Verify secrets are redacted and trace output is size-limited.
5. Run the existing test suite; do not change production data or deploy as part of explorer development.
